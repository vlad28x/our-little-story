## Скачивание копии внутри Telegram

После сообщения владельца об отказе скачивания JSON в Mini App обычный Blob-download оставлен браузеру, а все кнопки экспорта прогресса в Telegram открывают панель с «Скачать через браузер» и «Скопировать текст копии». Первый вариант передаёт выбранную копию через fragment текущего Pages URL в отдельную страницу, где нужно нажать «Скачать файл». Она не читает/не изменяет браузерный прогресс и не запускает синхронизацию. Вторая возможность и ручное выделение доступны при отказе браузера/clipboard. «Вставить текст копии» в настройках проверяет JSON и просит обычное подтверждение замены. Схема сохранений, интервал CloudStorage и сюжет не менялись.

Это решение для статического сайта без загрузки личного файла на сервер. Штатный [Telegram.downloadFile](https://core.telegram.org/bots/webapps#downloadfileparams) требует HTTPS URL файла: blob/data и API callback не заменяют такой файл. Поэтому Mini App использует официальный openLink для отдельного браузера. Payload ограничен внутренней длиной URL 60000, большие копии остаются доступны текстом; fragment удаляется из адреса после чтения. Нельзя обещать успешное сохранение файла по факту вызова openLink: пользователь должен увидеть страницу и нажать «Скачать файл». Проверка реального системного открытия Telegram остаётся за владельцем; автотесты используют тестовый SDK.

## Что реализовано

- Официальный telegram-web-app.js загружается только при параметрах запуска Mini App или уже предоставленном initData. В обычном браузере нет запроса SDK. При неудаче/таймауте есть повтор и локальный режим.
- ready/expand, цвета шапки, safe-area, нативная BackButton: в сцене открывает паузу, на других экранах возвращает на карту. Во время неподтверждённой облачной записи включено подтверждение закрытия.
- Перед игрой читается облако. На новом устройстве валидная история восстанавливается автоматически; при одинаковых локальной/облачной копиях сохраняется локальный continuation. Если копии различаются, выбор явный; обе можно скачать до выбора. Никакого выбора по большим revision/дате устройства.
- В первом запуске пустого облака объясняется, что история будет сохраняться в Telegram; можно выбрать локальный режим. Существующий браузерный прогресс автоматически к аккаунту не привязывается: есть явный перенос, если он доступен в этом WebView, и прежний импорт JSON в настройках.
- Локальный ключ: `five-meetings:<BASE_URL>:telegram:our_little_story_game_bot:<userId>:save`, backup — замена суффикса. Обычный браузер, другой Telegram-аккаунт и dev разделены. userId из launch data — только разделитель локального кеша, не серверная авторизация. initData не сохраняется и не логируется. Серверных API, доверяющих initDataUnsafe, нет.
- Сохранения отправляются после действий с debounce 650 мс, сериализованной очередью; при сворачивании — дополнительная попытка. Локальная запись остаётся после каждого действия. Интерфейс показывает подтверждённый успех, ожидание, ошибку или локальный режим. Последние действия при закрытии до подтверждения облаком могут оставаться только локально.
- В облако входят сюжет, trial, альбом, настройки и права глав. Журнал прочитанных реплик удалён из игры и новых сохранений. `continuation` всегда заменён на null: реальное согласие/отказ и черновики сообщения остаются на устройстве. PNG и JSON для ручного переноса не получают Telegram-идентификаторы.
- После транспортной ошибки облачная запись приостанавливается до повторной проверки; пустая игра не подменяет неизвестное облако. При изменении удалённой копии игра ставится на паузу, доступно скачивание и повторное сравнение. При повреждённой копии можно явно восстановить предыдущую или выбрать локальную. Состояние schemaVersion/contentVersion и сценарии не меняются.

## Формат облачной записи

Документированный предел CloudStorage — 1024 ключа на пользователя/бота и 4096 символов на значение; на реальном Telegram Desktop получен DATA_TOO_LONG при передаче русскоязычной части из 3500 UTF-16 единиц. Новые части ограничены консервативным бюджетом 3000 байт UTF-8 для JSON-строки значения, включая кавычки и экранирование. Это оставляет место для имени ключа и обёртки запроса. Используются два фиксированных банка a/b и `five_meetings_v1_head`. Ключи соответствуют `[A-Za-z0-9_-]` и короче 128 символов. Верхняя граница — 176 частей на банк и один head (353 ключа); getItems получает не более 32 ключей за запрос. Не создаются бесконечные поколения ключей.

Head: `{version:1,current:{slot,count,length,hash},previous:Part|null}`. Запись: проверить expected head → записать неактивный банк → прочитать и проверить SHA-256, длину и parseSave → повторно проверить head → опубликовать новый head → подтвердить чтением. Предыдущий валидный банк сохраняется. Восстановление из backup также не перезаписывает единственную валидную копию до commit. Все операции callback имеют таймаут 20 секунд (увеличен с 8 при расследовании сбоя Telegram Desktop). Лимит envelope сохраняется 256 KiB по правилам текущего валидатора.

CloudStorage не предоставляет compare-and-swap: поддерживается одно активное устройство/вкладка. Проверки head и фокуса обнаруживают обычные конфликты; полностью одновременную гонку двух писателей нельзя гарантированно устранить без сервера. Абсолютная вечная сохранность не обещается, JSON-резервирование остаётся доступно. Обычный Chrome не получает облако Telegram; для общей авторизации браузера нужен отдельный сервис.

Сам скриншот не позволяет определить причину: прежнее сообщение «Облако не ответило» скрывало и отказ API, и неподтверждённую запись, и ошибку проверки копии. Не называть все такие случаи отсутствием сети и не считать конкретную причину подтверждённой по заглушке.

Теперь баннер говорит «Сохранение в Telegram не подтверждено. Прогресс остаётся на устройстве». В раскрываемом блоке «Почему не сохранилось?» показаны стадия (чтение состояния/частей, запись части или подтверждение) и короткий машинный код ошибки. Неизвестные тела ошибок скрыты за API_ERROR/CHECK_FAILED: в UI и консоль не попадают initData, профиль, ключи или содержимое сохранения. Отсутствие WebCrypto отмечается HASH_UNAVAILABLE, а не повреждением облачной копии. Успех по-прежнему требует чтения, SHA-256 и parseSave. Протокол, ключи и версии сохранений не менялись; автоматических повторных записей после отказа нет.

Таймаут callback увеличен до 20 секунд: тест подтверждает принятие ответа через 12 секунд и остановку зависшего клиента. Проверены безопасное отображение кода, фильтрация произвольного тела ошибки и сохранность двух копий после отказа записи. Изолированный тест воспроизводит последовательность «разные истории → выбрать устройство → отказ записи → открыть причину → продолжить локально». ### Исправление DATA_TOO_LONG

Владелец сообщил точный код из Telegram Desktop: «Запись части сохранения: Telegram не подтвердил запрос (DATA_TOO_LONG)». На тестовом native API с ограничением сериализованного запроса 4096 байт воспроизведён отказ старой русскоязычной части из 3500 символов. Это размер транспортного фрагмента, а не потеря истории и не доказательство повреждения старой копии.

splitCloudText теперь считает UTF-8 размер JSON-строки каждого code point, включая экранирование кавычек, обратных слешей и управляющих символов. Бюджет 3000 байт, emoji не делятся между частями. Сам исходный JSON, SHA-256, длина в head и схема envelope не изменены. Reader принимает старые части до 3500 UTF-16 единиц, новый count и смешанные поколения current/previous; расширение count ограничено 176 частями, проверка целостности и parseSave прежние. Большие банки читаются порциями до 32 ключей, чтобы список ключей тоже не создавал слишком большой запрос. Новые записи по-прежнему идут в неактивный банк; head меняется только после подтверждённой проверки.

Регрессии: старый Cyrillic-фрагмент получает DATA_TOO_LONG, тот же активный прогресс проходит новое разбиение; полная история пяти глав; кириллица/emoji/JSON escapes; большой валидный импорт и пакетное чтение; чтение legacy-банка, оборванное обновление без смены head и последующая запись с прежним backup. Браузерный тест: разные локальная/облачная истории → выбрать устройство → успешно записать длинную главу через ограничение 4096 байт → восстановить тот же курсор во втором клиенте. Реальные сохранения владельца в проверках не используются; подтверждение настоящим Telegram после обновления остаётся за владельцем.

### Журнал прочитанных реплик удалён

По новому поручению автора удалены меню «Прочитанные реплики», модалка и накопление текстов в runtime, локальных новых сохранениях и CloudStorage. Это не режим «журнал только на устройстве»: журнал вообще больше не ведётся. Старые JSON с журналом в campaign.active и trial.run проверяются и нормализуются без изменения остального прогресса. cloudRaw/persist используют эту нормализацию; экспорт содержит компактную модель.

При чтении облачной копии legacy hash проверяется до удаления поля. needsRewrite заставляет CloudSession подтвердить запись компактного варианта в неактивный банк с неизменным revision, даже если игрок ещё не нажал «Дальше». Равные по прогрессу копии с разными журналами считаются одинаковыми; реальные отличия по-прежнему требуют выбора. Оригинальная предыдущая копия остаётся резервной до обычной ротации, чтение локального файла само по себе его не перезаписывает. Не считать старые отчёты о передаче журнала текущим поведением.

На прикреплённом владельцем файле проверено точное равенство всех полей после удаления journal: размер компактного cloud JSON 2451 байт вместо 11636. Файл владельца и его содержимое не включены в тестовые фикстуры, репозиторий или public. Синтетические проверки покрывают active/trial всех пяти глав, старые contentVersion1–4, JSON-импорт/экспорт, продолжение, отсутствие пункта меню и автоматическое обновление облачной копии без ложного конфликта.
