# Инструкции для следующего разработчика

Три одобренные пасхалки реализованы в SceneEasterEggs и content/easterEggs.ts: кудри, Пончик, печенье дома. Это только UI, без engine commands, новых флагов, сохранений или CloudStorage. Не связывать поглаживание с cat-supervisor: прежний секрет выдаётся за кота в TokenSearch и завершение главы. Не включать пасхалки в мини-играх, на паузе, в обложке/результате/InvitationPanel или поверх ошибки загрузки арта. Тексты, доступность и границы — SCENE_EASTER_EGGS.md; четыре интеграционных теста входят в test:offline. cookieTaken принадлежит SceneStage, а не условно смонтированному SceneEasterEggs: кухня/пауза не должны возвращать третью печеньку. Уход с экрана истории/reload сбрасывает только косметику. Сценарии/версии сохранения прежние.

После переименования репозитория в our-little-story прежний прогресс `/little-projects/` читается как fallback при отсутствии новых save и backup. Не убирать эту совместимость. Старые JSON остаются нетронутыми, новые действия пишутся по текущему base; другие проекты и dev-режим не наследуют прогресс.

## Задача и статус

«Пять случайных встреч» — небольшая русскоязычная мобильная визуальная новелла на React + TypeScript + Vite для GitHub Pages. Реализованы главы 1 (31 узел, три финала, поиск жетонов) и 2 (37 узлов, два финала, пазл зонтика), а также глава 3 (33 узла, 78 реплик, четыре исхода кухни), сохранения/резервная копия/импорт, пробное прохождение и альбом. Подключён сгенерированный арт; базовый chibi-образ Влада одобрен автором в чате. Глава 4 также реализована (30 узлов, 83 реплики, созвездие, два финала). Глава 5 реализована (32 узла, 83 реплики, альбом воспоминаний и четыре финала); игра опубликована 18 октября 2026 на https://vlad28x.github.io/our-little-story/ (репозиторий https://github.com/vlad28x/our-little-story). Фактическое устройство и команды — в корневом README.md; исходный план ниже сохраняется как руководство дальнейшей работы.

Этапы A–D IMPLEMENTATION_PLAN уже послужили основой первой главы. Не создавать её заново. Не распараллеливать работу между агентами без прямого разрешения пользователя. Простые решения важнее количества модулей.

Вторая и третья главы готовы по отдельным поручениям. `src/content/chapters/index.ts` — реестр реализованных глав; доступны 1–5. Глава 2 требует завершения первой и права открытия (только код из личного сообщения автора; свободного открытия нет). `schemaVersion:1`, `contentVersion:5`; старый контент 1–4 валидируется в прежних границах и мигрирует в parseSave без изменения прогресса. Не ломать обратную совместимость, не сбрасывать чужие копии молча. Третья требует завершения второй и отдельного кода автора. Точные реплики — CHAPTER_02_SCRIPT.md, CHAPTER_03_SCRIPT.md и CHAPTER_04_SCRIPT.md; узлы и реплики сверяются с соответствующими TS-файлами. Четвёртая требует отдельного кода и завершённой третьей.

Если изменяешь контракт типов/флагов, синхронно меняй сценарий, документацию и проверки. Не вводить скрытый альтернативный дизайн.

## Технические ограничения

1. React, TypeScript strict, Vite, обычный CSS; runtime-зависимости по умолчанию только react/react-dom. Без backend, Firebase, Supabase, БД, логина, аналитики и тяжёлого игрового движка. По новому поручению разрешён официальный Telegram WebApp script и CloudStorage только для Mini App; сторонний SDK-пакет не добавлен.
2. Сценарий — типизированные данные; step чистая; UI отображает состояние. Не размещать диалоги и условия всей истории внутри JSX.
3. Узлы dialogue/choice/route/minigame/end. Сохранять IDs, выбирать эффекты по закрытому словарю. Не eval и не JavaScript в импортируемом контенте.
4. Одно направление состояния: reducer → новая версия → persistence. Не менять сюжет из таймеров UI, аудио и анимаций.
5. Сохранение после каждого логического действия; двойной тап защищён expectedTurn. Один envelope, backup, валидация, экспорт/импорт; нельзя молча обнулить несовместимое сохранение.
6. Коллекция, trial и текущая история разделены. Пробный повтор не переписывает канон. Изменение истории удаляет последующие результаты только после понятного подтверждения.
7. GitHub Pages base из единого config; все public assets через BASE_URL. Hash-навигация, никаких серверных rewrite. Проверять сборку из подпапки и refresh.
8. Dev-панель изолирована от production и обычного сохранения. Не хранить настоящие секреты во frontend env.
9. Версии зависимостей фиксировать lockfile; новые пакеты добавлять только для конкретной недостающей возможности, объясняя причину.
10. Не создавать заранее пустую структуру всех будущих модулей. Глава 1 работает при `available:false` остальных глав.

## Сценарий и персонажи

- Влад — художественная версия автора: 26 лет, backend, игры, бассейн, короткая разговорная речь, самоирония и забота поступками. Не идеальный соблазнитель и не человек, требующий постоянного утешения.
- Узнаваемый рисунок: слегка вытянутое лицо, объёмные светло-каштановые кудри, выразительные брови, стройное тело. Использовать единый модельный лист.
- Голос Влада преимущественно lowercase с нормальной орфографией. Не спамить «ахах», вопросами, прозвищами и программистскими метафорами.
- Героиня самостоятельна, не обязана флиртовать, спасать самооценку героя или соглашаться на дом. Не описывать её влюблённость как факт без выбора.
- Никаких очков любви/совместимости/правильности границ. Мини-игровой результат влияет на событие, а не достоинство игрока или доступ к отношениям.
- Четыре общих финала выбираются явно и доступны всем. Приглашение в жизнь появляется отдельно и не зависит от очков.
- Глава 3 происходит в уютной квартире Влада: диван, телевизор, плед, напитки, вкусняшки и два Xbox-геймпада. Предварительная договорённость героев — часть вымышленной истории, не согласие игрока на реальную встречу. После главы 5 реальное приглашение повторить вечер добровольно; киновечер, кафе, прогулка и явный отказ остаются доступными без условий по финалу.
- Сцену разряженного второго геймпада переносить по точным репликам GAME_DESIGN: уверенная подготовка → нажатие → «полтора геймпада» → tease/help/absurd → запасные батарейки → общая игра. `controllerReaction` меняет действие перед обучением и реплику-память главы 5. Сохранять остальные ветки, kitchenStyle, результаты кухни и четыре финала; не добавлять новый игровой движок, тип мини-игры или очки отношений ради этого эпизода.
- Каждое добавленное сюжетное поле имеет конкретное последствие; не плодить состояния ради будущей гипотетической сложности.
- Реплики пяти глав не заменять резюме. Точный реализованный сценарий пятой — CHAPTER_05_SCRIPT.md; её 32 узла и 83 реплики сверяются тестом с ch05.ts.

## Арт, приватность и коммуникация

- Оригинальные шесть фотографий и профиль Telegram не включать в public, git, dist, экспорт сохранения или поставляемый архив. Работать с художественными производными и обезличенными правилами.
- Не публиковать сведения о реальных собеседницах, адрес автора, телефон, переписки и другие ненужные личные детали.
- Не выдавать плейсхолдер за готовую иллюстрацию. До массового арта показать автору лист модели; пока он проверяет сходство, продолжать независимые технические задачи.
- У всех сторонних ассетов есть источник/лицензия. Игровой арт не должен копировать конкретную коммерческую игру.
- Никакой автоматической отправки в Telegram и скрытого сбора. Share/copy/download запускаются только отдельным действием. Не считать закрытие share доказательством отправки.
- Контакт и репозиторий неизвестны: не придумывать username/адреса. Реальный выбор continuation по умолчанию остаётся только на устройстве.
- Не создавать репозиторий, не push и не публиковать сайт без соответствующей авторизации пользователя. Локальную работу, исправления и проверки делать в пределах порученного этапа без лишних вопросов.

## Мобильность и доступность

От 320 px ширины; safe-area, динамическая высота, текст 18 px, цели ≥48 px. Выборы без таймера. Управление тапами вместо обязательного drag; keyboard и focus. Системный reduced motion, звук выключен по умолчанию. Кухня имеет полноценный спокойный режим и пропуск. Сворачивание ставит таймер на паузу. Никаких обязательных аудиоподсказок.

Не обещать поддержку каждой версии Telegram по результату одного desktop-теста. Web Share, clipboard и download проверяются по возможностям и имеют ручные варианты. Прогресс разных браузеров не синхронизируется; для переноса есть JSON.

## Готовность работы

Перед отчётом выполнить проверки, относящиеся к изменению: typecheck, логика ветвлений, целостность графа, save/replay, production build и нужные browser smoke. Не писать десятки тестов декоративных классов. Не сообщать о проведённых тестах без фактического запуска.

Глава 1 готова только когда все её окончания пройдены, эффекты видны, мини-игра работает, арт согласован, reload/import/export/replay проверены, мобильный интерфейс удобен. Для публикации дополнительно нужны реальный URL и проверка на нём. В отчёте коротко указать работающие возможности, проведённую проверку и оставшиеся ограничения.


## Реализованная четвёртая глава

ConstellationResult = {kind:'constellation',outcome:'cat'|'controllers'|'teapot',usedPreset:boolean}. Готовая картинка только teapot; false выдаёт own-sky. В story главы четыре поля bench/constellation/bond/wish. CardRecord четвёртой хранит usedPreset, variant — силуэт; канонический результат восстанавливать через cardFromStory(story,chapter,record.results), а не брать последний вариант из коллекции. Bench влияет на композицию, bond не закрывает будущие финалы. Код четвёртой не показывать в общедоступной документации. Все ассеты регистрировать явно в manifest до экспорта: не возвращать заполнение поздними циклами, которое сопровождало сбой vlad.casual.smile.

Браузерный прогон четвёртой выполняется также через test:offline в изолированном документе без сети, с файлами data URL и тестовой памятью. Не использовать его для доступа к пользовательской вкладке или её сохранениям. Публикацию и реальное устройство проверять отдельно.

MemoriesResult = {kind:'memories',outcome:'viewed'|'skipped'}. Расстановка трёх жетонов локальна UI, результата в story нет. При completed5 канона он доступен после любого финала, включая завершённый trial; активный trial и просмотр альбома исключены. Это эпилог UI, не обязательный узел графа и не часть PNG. Три части: подводка по ending, геймпады с controllerReaction, форматы встречи. Пять ответов видны на каждой части и остаются после реакции: game/movie/cafe/walk/decline. Прогресс чтения подводки локален UI; continuation сохраняется обычным действием, не меняет ending/открытку. Ни отсутствующий ответ, ни уход с экрана не означают отказ. ## Заметный ввод кода на карте

Ввод кода — постоянно раскрытый section.code-entry вверху карты, перед chapter-list. Не возвращать его в details внизу. У закрытых глав есть «Ввести код»: прокрутить к полю и передать фокус без автоматической проверки/открытия. После успешного кода — явная кнопка перехода при выполненных условиях, без автозапуска. ## Telegram Mini App

По поручению 18 октября 2026 добавлены TelegramEntry, bridge, cloud и useCloudSync; детали и инструкция BotFather — TELEGRAM_MINI_APP.md. Бот владельца @our_little_story_game_bot. Обычный сайт и dev остаются локальными, SDK загружается только при запуске Mini App. Не публиковать токен, initData и Telegram-профиль. userId используется только для изоляции кеша; серверной авторизации нет. CloudStorage API само ограничивает данные аккаунтом/ботом.

Облако двухбанковое: части по 3500 символов, head последним после read-back/SHA-256/parseSave. Сохранять ожидаемый head и сериализацию, не заменять неизвестную облачную копию пустой. При расхождении локальной и удалённой историй выбор явный с экспортом; никакого сравнения только revision. Транспортная ошибка оставляет локальный режим без автоматического overwrite. continuation в cloudRaw всегда null; реальные приглашения остаются на устройстве. Не переносить обычный браузерный прогресс в Telegram-аккаунт без выбора. Нельзя обещать синхронизацию обычного Chrome или транзакционность между одновременно активными устройствами. Сценарии и schemaVersion/contentVersion не изменились.

test:unit включает telegram.test.ts, test:offline — telegram-offline.spec.ts. Заглушка SDK — не реальная проверка Telegram. Настройку BotFather и два реальных клиента подтверждает владелец; не выдавать эту проверку за сделанную автоматически.
